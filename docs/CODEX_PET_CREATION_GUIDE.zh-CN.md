# 如何制作一个精美的 Codex 宠物

这份指南把一次真实 Codex 宠物制作过程中踩过的坑整理成可复用清单。最终案例的私人创作 prompt 和可识别设计细节会有意省略。

## 1. 先理解 Codex 宠物格式

Codex 宠物不是简单的 GIF。它通常由两个文件组成：

- `pet.json`
- `spritesheet.webp`

`spritesheet.webp` 是一张动画图集，由固定尺寸的小格子组成。在我们的流程里，每一格是：

```text
192 x 208 px
```

常见完整图集有 9 行状态：

```text
0 idle
1 running-right
2 running-left
3 waving
4 jumping
5 failed
6 waiting
7 running
8 review
```

每一行包含这个状态下的多帧动画。Codex 会读取对应行并播放这些帧。

## 2. 一开始就告诉用户有哪些状态

很多用户一开始并不知道 Codex 宠物有不同状态。不要等到最后才告诉用户。

在生成状态图或动画横条之前，先向用户说明状态契约：

| 行 | 状态 | 含义 |
| --- | --- | --- |
| 0 | `idle` | 默认待机状态 |
| 1 | `running-right` | 向右移动或拖拽 |
| 2 | `running-left` | 向左移动或拖拽 |
| 3 | `waving` | 打招呼 |
| 4 | `jumping` | 跳跃或兴奋反应 |
| 5 | `failed` | 任务失败或需要恢复 |
| 6 | `waiting` | 等待用户输入或确认 |
| 7 | `running` | 任务处理中，不是字面意义的跑步 |
| 8 | `review` | 检查或 review 结果 |

然后询问用户：是否使用默认动作，还是想自定义某些状态。

可使用这个模板：

```text
templates/state-action-plan.template.md
```

在用户确认默认状态方案或自定义方案之前，不要开始生成状态图。

## 3. 先确定宠物，不要一上来就做 spritesheet

不要一开始就要求生成完整 spritesheet。更稳的做法是先创建或导入并确认一张标准宠物参考图。

根据素材选择入口：

1. **纯文字概念：** 先生成一张基础宠物图，再制作状态行。
2. **已有参考图片：** 选择或整合成一张经过确认的视觉基准。
3. **动物、物品、植物、机器人、吉祥物或抽象主体：** 描述轮廓、材质、标记、附着特征、配色和运动，不强行套用人形结构。
4. **已有横条或 spritesheet：** 保留已经认可的身份，只修复失败的动画行或打包步骤。

把通过确认的基准保存为 `canonical-reference.png`，并记录：

- 宠物类型或主体
- 轮廓和比例
- 表面或材质
- 标记和附着特征
- 配色
- 性格或整体感觉
- 禁止变化项
- 左右不对称特征和动作规则

只有当标准参考图在 `192x208` 下仍可读、主体形态完整、没有意外文字或特效，并且包含所有必须保持一致的特征时，才批准它进入下一步。

图片可以来自 Codex 生图、其他图片工具或用户提供的文件。本仓库的 Python 脚本不会凭空生成视觉作品，只会确定性地处理已有横条。把导入的状态参考图保存在项目自己的目录中，例如 `20-states/`；源横条使用状态名命名，例如 `idle-source.png`。

如果图片模型无法稳定生成准确数量且彼此分离的姿势，不要偷偷复制帧。应简化动作、缩小宠物并增加间距后重试；可以先用 4 或 6 帧验证动作思路，但最终图集固定为 8 列，因此生产行需要重新生成完整 8 帧。

## 4. 让角色适合 192x208 的小尺寸

好看的插画不一定能在 `192x208` 里保留清晰效果。

适合做宠物的设计通常需要：

- 轮廓清楚
- 大形状简洁可读
- 表情或视觉焦点清楚
- 小型附着细节不要太多
- 避免细长飘带和松散装饰
- 不要漂浮特效
- 不要阴影或柔光
- 主体形态完整可见并留有安全边距

宽轮廓、拖尾、叶片、尾巴、触角、线缆或道具必须足够紧凑，不能在动作中超出每一帧边界。

一个实用规则：

```text
宠物高度大约占最终格子高度的 75-85%。
```

动作幅度大的状态要让姿态更紧凑，宠物也可以稍微小一点。

## 5. 先定义状态动作，再生成动画行

不要让每个状态变成随机可爱姿势。每个状态都应该有明确语义。

请用用户自己的方案填写动作：

| 状态 | 含义 | 用户动作 |
| --- | --- | --- |
| `idle` | 默认待机 | …… |
| `running-right` | 向右移动 | …… |
| `running-left` | 向左移动 | …… |
| `waving` | 打招呼 | …… |
| `jumping` | 开心反馈 | …… |
| `failed` | 任务失败 | …… |
| `waiting` | 等待用户 | …… |
| `running` | 任务处理中 | …… |
| `review` | 检查结果 | …… |

特别注意：

- `running` 不是字面意义的跑步，而是“任务处理中”。
- `running-right` 和 `running-left` 才是方向移动状态，可以使用任何适合宠物形态的紧凑移动方式。
- `waiting` 不要和 `running` 重复，两者的意图必须一眼可区分。

## 6. 先生成状态参考图，再生成动画横条

状态参考图是单张图，用来确认某个状态的动作概念。它能帮助后续多帧动画保持稳定。

推荐顺序：

1. `idle`
2. `running-right`
3. `running-left`
4. `waving`
5. `jumping`
6. `failed`
7. `waiting`
8. `running`
9. `review`

每张状态参考图都要检查：

- 还是不是同一个宠物？
- 标志性标记和附着特征有没有保留？
- 小尺寸下主体形态是否清楚？
- 姿态是否符合状态含义？
- 有没有东西伸得太靠左或太靠右？
- 有没有新增道具导致最终 sprite 太宽？

## 7. 动画横条使用纯色抠图背景

生成动画横条时，使用纯色 chroma 背景。我们使用的是：

```text
#FF00FF
```

提示词里应要求：

- 一张横向 strip
- 明确帧数
- 每帧之间有足够宽的纯色间隔
- 不要标签
- 不要边框
- 不要参考线
- 不要阴影
- 不要运动特效
- 不要漂浮符号
- 每帧主体形态完整可见

原因是最终宠物需要透明背景。干净的纯色背景才能稳定地用代码去除。

## 8. 帧与帧之间必须留足间距

我们遇到过一个很重要的问题：帧之间互相串图。

典型表现是：

```text
第一帧的拖尾特征出现在相邻帧里。
```

这通常是因为模型生成横条时把宠物排得太近。后续切图时，隔壁帧的一部分就会被切进去。

生成时要明确要求：

- 很宽的纯色空白间隔
- 宠物整体小一点
- 轮廓和附着特征更紧凑
- 不要大幅拖尾的细节
- 宠物部件和道具不要贴近帧边缘

不要只看原始横条。必须实际切成 `192x208` 后再检查。

后续生成提示词建议使用：

```text
docs/SPRITE_STRIP_SPACING_RULES.md
```

核心规则：

```text
每两个相邻姿势之间至少保留 80px 的纯 #FF00FF 背景。
如果宠物或道具太宽，就整体缩小宠物和道具，不要压缩间距。
```

## 9. 一定要切成 192x208 后预览

不要只看生成出来的横条就批准一行。一定要切成最终格子并预览。

使用：

```bash
python3 scripts/cut_strip_to_cells.py \
  --src <strip>.png \
  --prefix <output-prefix> \
  --frames 8 \
  --mode smart-components
```

脚本会生成：

- `<prefix>-cell-preview.png`
- `<prefix>-192x208-transparent.png`
- `<prefix>-preview.gif`
- `<prefix>-metrics.json`

这些都要看。

AI 生成的横条优先使用：

```text
--mode smart-components
```

这个模式会先识别整张横条里每个宠物组件的真实边界，再裁剪。这样可以避免等宽切图线把附着特征切掉。

只有在源图严格按照网格生成、每一帧都确定没有越界时，才使用 `--mode equal-slots`。

当前脚本还会检测相邻组件之间的真实间距。如果源横条太紧，会在 `<prefix>-metrics.json` 里写入：

```text
spacing_summary.min_gutter_px
spacing_summary.warnings
component_diagnostics[].effective_padding_px
```

默认情况下，`smart-components` 会自动调整左右 padding。也就是说，即使你传入 `--component-padding 22`，如果隔壁帧离得太近，脚本也会自动缩小左右 padding，避免把隔壁宠物部件或道具切进来。

严格 QA 时可以加：

```text
--fail-min-gutter-px 24
```

这样如果检测到帧间距小于 `24px`，脚本会直接失败，提醒你重生成更宽间距的源图。

## 10. 去除隔壁帧碎片

即使提示词写得很好，等宽切图仍然可能截到隔壁帧的一点碎片。

如果这个碎片和主体是分离的，不一定需要重生成，可以在后处理中去掉。

`cut_strip_to_cells.py` 会做：

1. 去掉洋红背景。
2. 检测连通组件。
3. 保留主体宠物组件。
4. 保留贴近主体的小组件。
5. 删除远离主体的碎片。

这样能避免某一帧的附着或拖尾特征出现在下一帧里。

## 11. 清理洋红边缘污染

另一个常见问题是洋红色光边：

```text
抠图后宠物像是带了一圈粉色光。
```

这是因为抗锯齿边缘像素混合了角色颜色和洋红背景。

缓解方法：

- 使用硬边、纯色背景
- 提示词要求 crisp edges 和 no glow
- 删除接近洋红色的像素
- resize 后对边缘颜色做 decontaminate
- 在棋盘格背景上检查

不要只在洋红背景上批准一行。很多边缘问题在洋红背景上会被隐藏。

## 12. 注意生成结果中的结构问题

AI 生成动画行时，经常会出现很小但很影响观感的结构错误，例如部件重复、形状粘连、孤立碎片、标记变化或道具穿过主体。修复 prompt 只描述实际缺陷：

```text
Keep the approved silhouette and attached features unchanged.
Remove the detached or duplicated fragment at: …
Keep these shapes visually separate: …
Do not move this marking or prop: …
```

修复 prompt 应只说明可见缺陷以及必须稳定的已批准特征，不要暴露或照搬另一只宠物的私人设计规范。

## 13. 判断什么时候用 4 帧，什么时候用 8 帧

帧数不是越多越好。

4 帧：

- 更容易生成干净
- 更容易保持间距
- 身体结构错误更少
- 对小尺寸桌面宠物通常已经够用

8 帧：

- 动作更流畅
- 表现力更强
- 更容易串图
- 更容易出现身体结构漂移

推荐策略：

1. 先生成 4 帧或 6 帧测试。
2. 检查风格、动作、结构和抠图。
3. 4 帧稳定后再扩展到 8 帧。
4. 如果某个动作一直失败，就简化或改变动作，不要硬拗，同时保留宠物身份和状态语义。

## 14. 只有语义安全时才镜像

把一个方向的动画镜像成另一个方向很诱人，但可能破坏角色身份。

镜像可能翻转标记、符号、附着特征、道具位置或不对称轮廓。如果左右身份特征重要，建议两个方向分别生成；只有宠物在小尺寸下足够对称并经过视觉检查后，才可以接受镜像。

## 15. 保持项目结构清楚

生成宠物项目很容易变乱。要把当前成果、旧实验和 debug 文件分开。

推荐结构：

```text
Project/
  README.md
  docs/
  templates/
  skill/
  10-references/
  20-states/
  30-sprite-tests/
  40-final-package/
  80-legacy/
  90-debug/
```

项目目录映射示例：

- 当前参考图在 `10-references`
- 状态参考图在 `20-states`
- sprite 测试在 `30-sprite-tests`
- 草稿包在 `40-draft-package`
- 旧版本在 `80-legacy`
- debug 图在 `90-debug`

## 16. 最终打包前 QA 清单

生成最终 `spritesheet.webp` 前，逐行检查：

- 是否还是同一个宠物
- 视觉焦点是否一致
- 材质和配色是否一致
- 标记和附着特征位置是否稳定
- 宠物部件和道具有没有被裁切
- 有没有串帧
- 有没有孤立碎片
- 有没有洋红光边
- 有没有白色 / 黑色背景残留
- 有没有阴影或发光
- 有没有文字或参考线
- 状态语义是否正确
- 每帧大小是否稳定
- 基线是否稳定
- `192x208` 下是否可读

动画行还要检查：

- 方向移动是否一眼能看懂
- 动作循环是否稳定、自然、有意图
- 有没有结构错误
- 有没有速度线或尘土特效
- 道具有没有突然出现或消失

## 17. 推荐完整流程

可复用流程：

1. 写下宠物概念或收集参考素材。
2. 向用户说明 9 个 Codex 状态。
3. 填写并确认状态动作计划。
4. 生成主形象参考图。
5. 反复调整，直到宠物在情绪和视觉上都正确。
6. 如果原图在宠物尺寸下太复杂，就简化设计。
7. 保存标准参考图。
8. 写宠物身份规范。
9. 生成每个状态的单图参考。
10. 做 `192x208` 尺寸适配预览。
11. 先为最难的动作状态生成 4 帧测试。
12. 切成透明格子。
13. 检查 cell preview 和 GIF。
14. 4 帧可行后再扩展到 8 帧。
15. 清理背景、边缘污染和碎片。
16. 重复处理所有动画行。
17. 合成最终 atlas。
18. 验证 atlas。
19. 生成 `pet.json` 和 `spritesheet.webp`。
20. 查看最终 contact sheet 和 GIF 预览。
21. 把旧实验移动到 `80-legacy` 或 `90-debug`。

## 18. 可复用的制作经验

最重要的可复用经验：

- 好看的源图不等于能做成小宠物。
- 宽轮廓或拖尾特征必须有严格边距。
- 横条必须实际切图验证。
- 不要只相信原始生成图。
- 洋红背景上看着没问题，不代表透明后没问题。
- 组件清理对 AI 生成横条非常重要。
- 只靠提示词无法解决所有问题，确定性的后处理是流程的一部分。
- 保留版本化输出，避免好结果丢失。
- 一旦宠物被批准，就立刻写宠物身份规范。
- 状态动作应该在生成图片前就和用户对齐。

## 19. 最终案例

Lanxi 作为最终视觉案例保留，公开包包含：

- 已验证的 9 行 `spritesheet.webp`
- `pet.json`
- `examples/lanxi/rows/` 下的精选动画行
- 英文和中文 README
- GitHub Pages 展示素材

通用指南会有意省略 Lanxi 的私人 prompt、造型规范和状态动作方案。剩下主要是发布前打磨：

- 在真实 Codex 环境里观察新版宠物表现
- 根据使用效果微调个别状态
- 公开仓库里只保留精选素材
- 将实验文件和 debug 文件保留在被忽略的 legacy/debug 目录中
